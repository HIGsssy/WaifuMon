## 1. Executive summary

The strongest reusable foundation is the dungeon engine's transaction boundary, not its current loot authoring schema. A live interaction locks the player's run, checks its step, evaluates a pure engine transition, applies grants, and writes claims, state, and history in one transaction. The independent `reward_claims` JSONB map already prevents rewards being repeated after retreat and re-entry. Equipment grants and progression-currency settlement add their own unique keys.

The current dungeon reward model is much narrower than the requested model: only separate `reward` activities carry rewards; they select up to two **expedition-kind** tables and a range of unbanked progression currency. They pay WaifuBux, inventory items (including charms), and equipment. They discard an expedition table's Essence and XP. Combat and dungeon bosses have no reward property, and affection is absent from dungeon plans, grants, and summaries.

There is no single global loot-table system encompassing World Encounters and vendors. The database `reward_tables` catalogue contains boss and expedition kinds. World Encounters use choice success/failure effect arrays; vendors use stock templates and purchases. Those systems share economy and equipment services, not that catalogue. Dungeon separation must therefore include expedition and guild-boss tables as well as avoiding encounter/vendor content.

**Proposed smallest reliable architecture:** a dedicated `dungeon_loot_tables` authoring catalogue with names, descriptions, optional categories/boss tiers, optimistic revisions, and a dungeon-specific typed reward model. Inline activity bundles combine guaranteed grants, independent chance entries, and repeated draws from reusable tables. At dungeon publication, embed the exact referenced table bodies and hashes in the immutable dungeon revision. New and resumed runs read those bodies, never the mutable catalogue. Reuse domain grant services and the existing locked claim mechanism; add a copy-targeted affection service operation and deterministic equipment-instance support where required.

**Principal blockers and defects:** publication currently freezes table IDs rather than contents; the table delete guard misses dungeon references; missing item grants are silently lost after a claim commits; live table validation can admit capped items that block a payout; publication omits transitive reward validation. Equipment choice is deterministic, but instance rolls and some underlying definitions remain live. None of these were fixed in this audit.

### 2.2 Roll semantics

Boss and expedition tables have independent **groups**. Each enabled group repeats `rolls` times; each repetition checks `chanceBasisPoints`, then selects one enabled item or equipment entry by normalized weight. Draws are with replacement. Item and gear entries compete within the same group. Disabling an entry redistributes its weight; it does not create a no-drop slot.

* A 100% group guarantees a selection, not every row. To guarantee several particular items today, author several singleton groups.
* An independent chance drop can be represented by a singleton group, but it is not a dedicated entry type. Several rows in one group are mutually exclusive on each draw.
* Items have fixed positive integer quantities. Equipment entries produce one instance. There are no per-item quantity ranges. Expedition table WaifuBux/Essence use inclusive integer ranges; a flat range is allowed. Dungeon progression currency also has an inclusive range.
* No-drop comes from failing a group's gate, disabling groups, or runtime skipping a group with no enabled candidates. A configured group must contain at least one item/gear row, but all can be disabled. Zero chance is legal and produces a roller warning. Expedition tables can have zero groups; boss tables require at least one.
* There is no explicit weighted `nothing` entry, nested-table entry, table-recursion mechanism, or affection entry in these schemas.
* Boss tables have guaranteed `buddyXp`; expedition tables can specify WaifuBux, Essence, WaifuMon XP, and player XP. These are table-level amounts, not inventory entries.

Evidence: `src/modules/content/schemas.ts:1579–1602,1621–1702,1710–1760,2605–2706`; `src/modules/expeditions/expeditionRewards.ts:200–317` (`rollExpeditionTable`); `src/modules/bosses/bossRewards.ts:171–249` (`rollBossRewards`). `rewardTableCore` shares schemas/validation/hash/selector helpers; it is not a universal roller or grant executor. The two rollers remain distinct.

**RNG:** shared `rollWeighted` handles selection. Expeditions derive named draws from MD5 of ID/purpose/salt; currency ranges use integer modulo of a 32-bit hash. Dungeon RNG derives seeds from run seed plus room/action/wave; the dungeon reward seed feeds the expedition roller with separate success/bonus namespaces. Table IDs are not part of the expedition purpose strings; Phase 2 multiple-table draws need stable reference-entry/draw identities to avoid correlated repeated rolls. Existing two-table dungeon calls have distinct namespaces. Source: `src/modules/expeditions/expeditionRandom.ts:83–147`; `src/modules/dungeons/engine/seeds.ts:21–37`; `src/modules/dungeons/engine/rewards.ts:43–74`.

### 2.3 Admin API, lifecycle, and seed behavior

`/api/v1/admin/reward-tables` supports list/get, item and gear references, validation, gear selector preview, create/update/reset/delete, export by kind, and import plan/apply. Reads are gated by `rewards.read`, writes by `rewards.write`. Updates lock rows and check expected revision; imports are transactional and bind expected revisions. The exported format is the shipped array, not a dungeon dependency bundle.

`revision` is an optimistic concurrency counter. Optional author-entered `version` is audit text; neither is an immutable historical table version. `writeRow` overwrites the body. There are no table name, description, category, or boss-tier fields in the strict schemas. Metadata tracks latest actor/time/hash, but this service has no append-only table-edit event store.

Deletion refuses shipped tables and tables referenced by its supplied boss/expedition sources. `src/index.ts:861–870` correctly supplies **live cached boss definitions**, not merely the shipped boss file. Dungeon drafts/revisions are absent from this reference API. Disabling is allowed with consumer warnings; dungeon warnings are consequently missing too. Dungeon start snapshots a disabled table as null (zero payout), unlike an expedition's required success table, which prevents deployment when disabled.

Seed behavior is already careful: per-row transactions and row locks; insert missing, update unchanged-from-seed, preserve diverged edits, adopt an edit matching shipped content. Portal-only tables absent from the shipped list are untouched. Reordering is hash-significant. Reuse this pattern if dungeon seeds are added, but do not feed dungeon authoring through the current boss/expedition seed list.

Evidence: `src/api/routes/v1/admin/rewardTables.ts:139–215` and endpoint registrations; `src/modules/rewardTables/rewardTableService.ts:194–203,286–317,390–461,487–544`; `src/modules/rewardTables/rewardTableStore.ts:184–261`; `docs/reward-tables.md:29–118`; `src/modules/dungeons/dungeonRunService.ts:419–450`.

**Preview capabilities:** the existing editor shows conditional row shares and eligible gear definitions, and validates without writing. It has no full-table Test Roll or expected-value/no-drop calculator. The dungeon sandbox is read-only but explicitly passes `rewardTables: {}`, so it currently simulates progression currency only, not actual table rewards (`src/api/routes/v1/admin/dungeons.ts:908–922`).

## 4. Dungeon combat and reward-claim lifecycle

### 4.1 Full existing path

1. **Publication:** `DungeonContentService.publish` locks the definition, checks draft revision, validates, hashes the definition, inserts an immutable `dungeon_revisions` row, and moves the published pointer. The DB trigger forbids revision UPDATE/DELETE. It saves references, not table bodies (`src/modules/dungeons/dungeonContentService.ts:521–571`; `src/db/schema.ts:3063–3087`; `drizzle/0059_dungeon_overhaul_foundation.sql:148–159`, `dungeon_revisions_immutable` function/trigger).
2. **Start/pin:** `startInTransaction` locks the player, checks unlock/active run/region, snapshots fighter and external dependencies, consumes allowance, and writes run `revision_id`, seed, fighter, and dependency snapshot atomically. Only one active run per player is permitted (`src/modules/dungeons/dungeonRunService.ts:741–809`; `src/db/schema.ts:3252–3305`).
3. **Combat:** `fightWaves` uses pinned fighter/enemies and seeded per-wave fights. After an intermediate win, HP/wave state persists; confirm waits for another interaction, auto continues within the same step. Defeat/stalemate follows defeat routing. Only the last successful wave produces the activity's `victory` outcome. Neither intermediate nor final victory grants a reward today (`src/modules/dungeons/engine/step.ts:301–366`). A dungeon boss uses exactly these combat fields/flow, not guild-boss payout logic.
4. **Separate reward activity:** `resolveWithInput` computes `run:<id>:<room>:<action>`, checks `rewardClaims`, and either reuses the plan or rolls it from the run seed and snapshot. New claims accrue unbanked currency and emit a secured-reward effect. Even a zero-result reward is recorded as claimed (`src/modules/dungeons/engine/step.ts:390–408`; `src/modules/dungeons/engine/rewards.ts:59–89`).
5. **Claim/grants commit:** `act` SELECTs the player-scoped run FOR UPDATE, steps, applies effects, persists state/claim map/secured receipts, and appends history. WaifuBux/items have no independent key; this transaction plus claim map is their protection. Gear keys are `dungeon:<claimKey>:<rewardIndex>` (equipment appends `:0`). There is no separate claims table or durable pending status (`src/modules/dungeons/dungeonRunService.ts:594–646,828–855,934–974`).
6. **Settlement:** progression currency is banked on extract/complete, or retained according to defeat/abandon settings. WaifuBux/items/gear already secured remain owned. Request namespace is `dungeon_run:v1:<id>:settlement`. Missing/disabled live progression currency causes recorded banking loss and a terminal run, not a deferred claim (`src/modules/dungeons/engine/step.ts:111–136`; `src/modules/dungeons/dungeonRunService.ts:649–670`).
7. **Summary/resume:** `runView` returns pinned fighter, recent activity and persisted secured grants; latest secured rewards are filtered by step. Discord buttons carry run/step and redraw on stale requests; summaries distinguish unbanked progression currency from secured loot. There are no Essence/affection fields yet (`src/modules/dungeons/dungeonRunService.ts:541–585`; `src/discord/dungeonPresenter.ts:196–253`; `src/discord/commands/waifumonDungeon.ts:253–279,298–319`).

### 4.2 Exactly-once behavior and its limits

**Existing good behavior:** same-step concurrent requests queue on the run lock; one commits, the rest are stale. An already finished run refuses further actions. The engine's step check is conditional on `expectedStep` being supplied (`src/modules/dungeons/engine/step.ts:475–482`), but normal action/move/extract Discord handlers supply it. Abandon omits it intentionally and still ends only an active run. Require expected step for any new mutating combat interface.

Completed rooms do not replay. Retreat resumes unfinished actions and can erase their navigation record; that is why the independent claim map matters. Migration `0060_dungeon_reward_claims.sql:1–15` added the map and backfilled reward plans from history, including claims erased by retreat. `follow` retains claimed reward records at `src/modules/dungeons/engine/step.ts:208–221`, but claim protection must never depend solely on that record.

Thrown grant failures roll back earlier grant writes, claim and cursor together. Retrying reconstructs the same table/currency/base-definition result. There is no background reward worker; retry is a new player interaction after an uncommitted failure. A lost Discord response after commit does not lose the reward: the run/secured state can be read again, while an old step is refused rather than replayed as a successful request receipt.

Inspected regression coverage: `tests/integration/dungeonRuns.test.ts:263–326` checks concurrent steps/rewards; lines 448–491 inject inventory failure and check rollback, concurrent retry, restart, three retreat/re-entry cycles, single payout and single claim. `tests/unit/dungeons/dungeonEngine.test.ts:37–61` checks retreat claim survival. Tests establish intended assertions only; no fresh pass result is claimed.

**Confirmed exceptions:** missing items are skipped and the claim commits; disabled/missing settlement currency is lost with an explicit receipt. Neither has pending delivery recovery. Those behaviors do not satisfy an unconditional promise of delivering every configured reward exactly once.

**Determinism limit:** table/currency/base gear choice is reproducible; instance multiplier/affix/combat bonuses are generated with the equipment service's RNG and current definition/affix/bonus catalogues (`src/modules/equipment/equipmentService.ts:700–723,935–978`). Grant-key replay freezes a **committed** instance. A rollback removes that instance, so a later attempt can roll different properties. Nothing in the inspected Discord path displays uncommitted rolls; this is a retry reproducibility gap, not proof of a player-visible reroll exploit. A chosen candidate snapshot contains key/name/slot/rarity, not the definition's roll ranges (`src/modules/rewardTables/rewardTableCore.ts:233–247,305–315`). Editing ranges during a run can therefore change a later instance even though its table and chosen key remain pinned.

### 4.3 Proposed combat integration and claim identity

Reuse the independent map, outer transaction, effects port, and claim-key helper. Add a reward bundle to `combat` and `boss`, invoking a shared claim routine **inside the final-wave victory branch before outcome routing**, never at fight start or intermediate waves. Defeat, stalemate, decline, and abandoning an unfinished fight create no combat-reward claim. A scripted defeat route that leads to a separate chest activity remains a separate authored reward, not combat victory.

**A new claims table or distinct per-wave claim identity is not required** for synchronous local grants. One pinned room/action already identifies one activity reward; the existing run/room/action key is sufficient because its activity has a stable ID. A standalone chest has its own action ID and cannot share that claim accidentally. No visit count, step number, wave number, or arbitrary request ID should enter the activity payout identity. Combat records can be deleted by retreat; the claim map must remain intact even if the same combat is fought again.

Version the new plan/read model and RNG logic while preserving legacy keys/plans. If a new key namespace is chosen, explicitly detect legacy claims; do not blindly remint rewards on old runs. Use stable reward-entry/table-reference/draw/copy IDs for new equipment keys rather than an unstable flattened list position.

Persist recipient, table hashes, actual grant receipts and bonus provenance along with the claim. Empty rolls are successful claims. The current all-or-nothing step is the smallest solution. If design instead requires combat victory to persist while delivery is blocked, a durable pending-claim state and worker/retry protocol becomes necessary: persist the full resolved plan once, retry only undelivered grants, and introduce per-grant idempotency for currency/items/affection. That is a materially larger design and an open decision, not a reason to build an outbox by default.

## 5. Affection and charm integration

### 5.1 Actual affection behavior

`DungeonFighter.waifuId`, species slug and display name are pinned from combat stats at start (`src/modules/dungeons/dungeonFighter.ts:25–38,65–75`; `src/modules/dungeons/dungeonRunService.ts:763–781`). Combat continues with that fighter if the active Buddy changes. `CollectionService.setBuddy` / `clearBuddy` do not block on a dungeon run; availability reasons include expeditions but no dungeon participation (`src/modules/collection/collectionService.ts:1126–1166`; `src/modules/collection/waifuAvailability.ts:61–72`). After a swap, the old fighter may also be released because ordinary release protects the **current** Buddy, favorites and deployed copies, not the pinned dungeon fighter (`src/modules/collection/collectionService.ts:827–888`).

`awardBuddyAffection` resolves the current owned/non-released Buddy, applies current `affection_gain`, locks the owned row, and increments affection. It has no per-award key and no gameplay/daily affection cap in that operation. Storage is an integer, so practical numeric bounds still matter. Affection does not award XP, change level or unlock level-based appearances in this path. Named stages are thresholds 10/25/50/100/200/400; crossing computation is a separate pure helper, not an automatic grant-service event (`src/modules/collection/collectionService.ts:1299–1358`; `src/modules/collection/affectionStages.ts:19–46`). Bonus rounding uses `Math.round`, not floor (`src/modules/buddyBonus/buddyBonusEffects.ts:271–282`).

Daily affection gifts are separate: one eligible roll per player/reset day, an active-Buddy affection tier and per-copy pity counter; gift items are chosen at generation, not reward grant. Direct affection must not invoke extra gift rolls (`src/modules/gifts/affectionGiftService.ts:7–33,115–147`; `src/modules/content/schemas.ts:1334–1347`). The collection affection mutation itself has no grant ledger or event emission; a dungeon integration must record its own receipt/history and explicitly define any downstream progression/activity events. Do not invent a cap, gift, milestone notification, XP award or unlock side effect.

### 5.2 Proposed integration

Use the pinned fighter copy as recipient, never whatever `players.buddy_waifu_id` says at victory. Add a narrow collection-service operation taking player and owned-copy ID, locking/verifying ownership and release status, and sharing affection validation/modifier/receipt logic. `awardWaifuXp` is an existing example of explicitly targeting a committed copy, but it is XP, not an affection substitute (`src/modules/collection/collectionService.ts:1420–1456`).

**Open bonus policy:** existing `affection_gain` uses the active Buddy; dungeon participants need an explicit rule. Recommended: capture the participating Buddy's relevant bonus at run start, apply the same integer rounding, persist base/final/bonus on the claim, and keep it unchanged across retries. This is an extension of current behavior, not a claim that pinning already exists. The same choice is needed for `essence_gain`. A dungeon `boss` does not automatically inherit guild-only `boss_reward_gain` (`src/modules/buddyBonus/buddyBonusEffects.ts:116–129`).

**Open ownership policy:** either reserve the participating copy for the active run, or allow swaps/releases and define the released-recipient outcome (blocked delivery or explicit forfeiture). Never silently redirect affection to another Buddy. Keeping live slot changes possible while reserving the participating copy is a plausible small policy, but requires approval and shared availability integration. Recipient receipts should include owned-copy ID, frozen name/species, base amount, actual amount, bonus and resulting affection. Claim guard and row write must share the transaction.

### 5.3 Charms

Capture charms are ordinary inventory definitions with capture-specific use metadata. `basic_charm`, `silk_charm`, `velvet_charm`, `prismatic_charm` are `category='capture'` (`content/items.json:4–98`). Capture modifiers, eligible rarities and guaranteed-capture fields live on item content (`src/modules/content/schemas.ts:217–255`). Other charm-like consumables also use inventory; author-facing grouping can use category/effect metadata without adding a separate charm wallet or grant service.

Awarding a charm only adds its stack. Do not activate buffs, consume it, trigger a capture, or convert its capture semantics into currency/affection. Use name search and a Charm filter backed by item metadata; do not infer grant type solely from a slug containing `charm`. Capture-item soft capacity is enforced by some acquisition flows (e.g. affection-gift claim), not `InventoryService.addItem`; dungeon rewards currently bypass that soft cap. Decide whether earned loot should retain that behavior. Hard `maxOwned` limits are enforced regardless and need authoring validation or an approved overflow policy.

## 6. Dungeon Loot Table isolation recommendation

| Option | Benefit | Cost/risk | Recommendation |
| --- | --- | --- | --- |
| Add `kind='dungeon'` to existing `reward_tables` | Reuses CRUD storage mechanics | Existing kind CHECK/union, schemas, seed-file dispatch, APIs and Portal assume exactly boss/expedition. Separate reward vocabulary and publication still need substantial special cases. A picker filter alone does not freeze content or isolate lifecycle. | Viable if all interfaces enforce the namespace, but not the smallest low-risk boundary here. |
| Dedicated `dungeon_loot_tables` | Explicit ownership/API/permissions/seeding; dungeon metadata and reward semantics evolve independently | One catalogue table/service and validation/where-used work; reuse utilities rather than copy domain grants | Preferred. |
| Inline-only rewards everywhere | Easy revision pinning | Duplicated boss tables, repetitive edits and poor reusable authoring | Use inline direct bundles, with reusable dungeon table references alongside them. |

Proposed catalogue record: stable portable key; name and description; enabled/archive state; optional category and boss-tier tags; typed reward body; optimistic authoring revision; canonical content hash; creator/editor timestamps and actor. Keep organization descriptive unless a later approved policy gives tiers mechanical meaning. Add append-only authoring events. Bound groups/entries/draws/quantities and total reward work; current group rolls and weights have no useful upper bound in their shared schemas.

Proposed activity bundle has three explicit lists: guaranteed typed grants; independent chance entries (each with its own percentage and stable ID); and dungeon-table draw references (stable ID, table key, draw count). Typed grants distinguish currency, inventory item, equipment selector and participating-copy affection. A charm is a filtered inventory item. Reuse the same bundle for existing standalone reward/chest activities; future event/rescue types may adopt it later without being built now.

Reusable tables can use the same direct reward vocabulary plus weighted pools; the exact allowed table body belongs to 2B. At minimum support weighted entries and an understandable no-drop gate. Avoid nesting tables in the initial phase: it adds recursion/cycle/dependency and probability complexity without a stated need. No author-authored instance properties: use the shared equipment selector and equipment generator.

Reads and pickers must query only this catalogue. Give dungeon authors a dungeon-scoped library and appropriate existing dungeon permission gates or approved new permissions, never make unrelated `rewards.write` access a hidden prerequisite. Shared item/gear/currency catalogues remain authoritative. New where-used checks include drafts and published content; archival must preserve historical embedded data. A library disable should stop future authoring/publication use, not zero a published revision's existing loot. If emergency stopping payouts is required, design and audit it explicitly.

## 7. Revision and import/export strategy

### 7.1 Publication pinning

Existing immutable revision content is real, but reward dependencies are mutable until run start. Publication validation checks only table ID/enabled state, not item grants or equipment selector eligibility (`src/modules/dungeons/dungeonContentService.ts:278–289,527`; `src/modules/dungeons/validation/dungeonValidation.ts:392–405`). A table edit also does not change `dungeonContentHash`; publishing an unchanged draft returns `unchanged` at `src/modules/dungeons/dungeonContentService.ts:530–534`. Therefore simply copying tables at publish without changing the hash/comparison model would leave a dependency-refresh bug.

**Proposed:** publish a self-contained reward dependency bundle with exact parsed table bodies, source keys/revisions, semantic hashes and reward logic version. Resolve it and validate transitive dependencies inside the publishing transaction. Lock referenced authoring rows consistently or use a coherent snapshot with revision checks; no validation/copy race. Include dependency semantics in the revision gameplay hash and draft-vs-published comparison. Dependency-only changes must be visible for review and capable of creating a new revision. Rollback selects the old embedded bundle.

Runs of that revision use the embedded data. Later catalogue editing/disable/delete affects neither old active runs nor new runs of that published revision. Do not silently update bundles. Inline bundles are already part of content and should be hashed too. Separate display-only layout/organization changes from gameplay hashes according to an explicit canonicalization contract.

**Equipment scope needs approval:** freeze selector candidate membership at publication if the same revision must have the same available gear; do not re-expand broad selectors against new target/server definitions. Current snapshots freeze candidates at run start only. Multiplier ranges, affix/combat-bonus rules and definition existence are still mutable at grant. For a fully immutable reward promise, snapshot/version those generation inputs and add narrowly scoped shared-service support to grant from a validated promise. At minimum document any live generation behavior instead of calling it fully frozen. Items' use behavior and display names can reasonably remain shared/live, but changes to identity, caps and grantability require compatibility handling. Currency enable/disable policy also remains an operational decision.

### 7.2 Packages and imports

Current package v1 has strict envelope/definition schemas; bundles enemies only. Reward dependencies carry `{kind:'expedition', id}` with **no source table hash/body**; item/equipment manifest arrays are currently empty (`src/modules/dungeons/package/dungeonPackage.ts:59–109,150–167`). Import does check target reward definitions and gear transitively, hashes reviewed target state, takes dependency share locks, and uses a request-bound durable receipt (`src/modules/dungeons/package/dungeonImportService.ts:259–285,332–354,463–498,520–570`). It explicitly warns that source definitions cannot be compared (`:396–403`). Thus an import can use a valid but completely different target table with the same ID. This is a documented v1 limitation, not an integrity bypass.

**Proposed package v2:** carry direct reward bundles and referenced dungeon-table definitions with canonical hashes; enumerate their transitive item slugs, currency keys, equipment selector keys/candidate requirements, and generation versions if promised. Recompute and verify manifest/bundle membership; reject omitted dependencies, unreferenced injected entries and conflicting hash/body claims. Export a published revision's embedded tables, not current library bodies. Draft export resolves the draft's current dependencies and reports missing ones.

Import plan compares hashes and reports missing/identical/different dependencies. Reuse identical content; create missing bundled dungeon tables explicitly; never overwrite a differing target automatically. Prefer a new portable key/remapping or content-addressed immutable snapshot for a differing incoming table. Explicit use-existing, if allowed, changes gameplay and must show the difference, rewrite references, compute a new hash and require fresh review. Region/item/currency/equipment dependencies may be promoted separately, but every missing/ungrantable transitive dependency must block publication; optional incomplete draft import must not masquerade as playable content.

Reuse the existing request receipt, actor/payload binding, dependency plan hash and all-or-nothing draft apply. Include table creation/decisions/locks in that same protocol. Lock identities deterministically, revalidate at apply, and require a fresh plan after any dependency change. Imports remain disabled/unpublished on create and do not touch active runs or published pointers. Increase package version rather than adding fields that old strict readers will reject unexpectedly; continue reading v1 with explicit legacy handling.

### 7.3 Legacy and seeds

Do not mutate old immutable revisions or erase their claims. Retain a legacy reader for existing run snapshots. For editable legacy drafts, offer an explicit conversion that copies referenced expedition table contents into dungeon records and translates old reward semantics. Preserve both success/bonus draws and **all** rewards from `equipmentRewardTable`: despite its Portal label, that table also pays WaifuBux/items (`src/modules/dungeons/engine/rewards.ts:66–74`; cache/boss content above). Do not introduce previously discarded Essence/XP as a side effect of conversion. Preserve claims and equipment/settlement namespaces for historical runs.

Catalogue-only imports/seeds must not alter expedition/guild-boss records. Start with insert-missing dungeon seeds, or deliberately adapt the existing hash-divergence rules with dedicated files and origin metadata. Never perform blanket replacement from exported staging content. Reviewed imports must surface proposed overwrites; a table matching a seed should not imply that existing published bundles follow future seeds.

## 8. Existing editor UX findings for Phase 2B

These are code-based findings, not a browser usability study.

* **Too much machinery for simple rewards:** a guaranteed item requires group ID, enabled switch, chance, rolls and weighted entry fields. Authors must understand singleton versus competing groups. `portal/src/features/adminRewardTables/RewardGroupCard.tsx:86–200` exposes all this without distinct guaranteed/chance/pool concepts.
* **The item picker already shows names:** `portal/src/features/adminRewardTables/RewardRows.tsx:125–149` is a native select over name-labelled items, not a numeric ID input. It lacks dedicated search/filter interaction, charm grouping and grantability detail. Avoid diagnosing it inaccurately as an ID-only picker.
* **Tables are ID-labelled:** schemas lack human names/descriptions/categories, and dungeon dropdowns expose expedition IDs (`portal/src/features/adminDungeons/ActivityCard.tsx:338–359`). “Extra gear reward table” is misleading because all of that table's WaifuBux/items also pay.
* **Conditional probability is easy to misread:** row shares describe the weighted pick only (`portal/src/features/adminRewardTables/rewardTableModel.ts:43–58`); group summaries show chance/roll counts but not overall chance of getting that item, expected quantity, or no-drop rate (`:66–81`). Small shares round to one decimal and can display as 0% despite positive weight.
* **Cross-page authoring and incomplete previews:** dungeon actions select a table elsewhere rather than configuring direct combat loot. The table editor validates deferred drafts and previews gear eligibility (`portal/src/features/adminRewardTables/RewardTableEditorPage.tsx:121–143`), but has no full Test Roll. The dungeon sandbox omits tables.
* **Missing authoring dimensions:** fixed item quantities, one gear instance per entry, no affection, no activity-level guaranteed bundle, no multiple reusable table references, no boss-oriented organization. Tables expose XP fields that dungeons do not pay.

Recommended author experience for Claude's 2B design session: one combat/boss Rewards area with visible “Awarded after all waves are won” timing and three sections: **Guaranteed rewards**, **Chance-based drops**, **Random loot pools**. Each chance row says it rolls independently; a pool explains “one weighted selection per draw” and repeats with replacement unless an approved different rule is implemented. Allow all three together. Keep stable IDs internal; authors edit names and descriptions. Offer searchable item names, Charm filters, searchable gear choices/selector preview, affection to the run's participating Buddy, quantity min/max with flat default, and reusable-table shortcuts next to direct rewards. Show draft dependency changes and the published table version being reviewed.

Probability examples must use the actual model. For pool gate `p`, entry share `s=w/sum(w)`, and `n` independent draws: per-draw entry chance is `p*s`, at-least-one entry chance `1-(1-p*s)^n`, expected entry selections `n*p*s`, and pool no-drop ` (1-p)^n` if every successful pick grants something. For independent drop chance `c` and inclusive uniform quantity `[a,b]`, expected quantity is `c*(a+b)/2`. Across independent sources, multiply miss probabilities; guaranteed positive rewards make whole-bundle no-reward probability zero. Merge duplicate item outcomes for summaries, and include any explicit no-drop weights in the calculation. Disabled/ungrantable pools are configuration errors, not the same as ordinary no-drop. Label bonus/eligibility assumptions; gear definition chance additionally depends on candidate count.

Test Roll must run the real pure resolver against a reviewed dependency snapshot with selectable seed and optional multi-roll statistics, record only simulated effects, and never call live grant ports. Distinguish “rolled no drop” from “not configured/ungrantable.” Player summaries should use **actual committed receipts**, identify the affection recipient and bonus, name charms normally, show unique gear instances, and distinguish banked/secured/unbanked currencies. Limit/truncate Discord output while retaining full structured history (`src/discord/dungeonPresenter.ts:209–253`). This is direction and constraints, not a full UI specification.

## 11. Open design decisions requiring approval

1. **Catalogue boundary:** approve dedicated dungeon tables and dungeon-scoped authoring permissions; decide category/tier vocabulary and whether tables need their own publish workflow. Proposed minimum is mutable authoring revisions plus immutable dungeon publication embeds, with no second table-publish step.
2. **Reward vocabulary and currency timing:** guaranteed/chance/pool bundles; item/equipment quantity ranges; explicit no-drop representation; WaifuBux/Essence immediately secured versus any banked resources; supported additional currencies. Keep existing progression-currency retention unless changed explicitly.
3. **Affection eligibility:** pinned participating copy; whether to reserve it during the run; behavior if released/unavailable; applicable bonus and snapshot timing. Approve any milestone/quest events separately from raw affection mutation. No existing dungeon rule answers these.
4. **Failure and caps:** synchronous all-or-nothing victory+grant versus persistent victory with pending delivery; capped items and capture soft cap; missing/disabled item/currency policy. Recommended first implementation keeps atomic delivery and rejects unsupported/capped content before publication.
5. **Immutability extent:** table bodies must freeze at publication. Decide whether gear candidate membership, multiplier/affix/bonus generation inputs and Buddy bonus tuning also freeze, and define deliberate emergency stops. Recommendation freezes mechanical reward inputs and keeps presentation metadata live.
6. **Conflict and legacy policy:** explicit copy/conversion of expedition references, v1 readers and old-run treatment; import conflict create/remap versus approved use-existing; transitive item/gear/currency promotion responsibilities. Never silently overwrite unrelated catalogues or old claims.
7. **RNG/claim contract:** versioned resolver with stable entry/reference/draw/copy identities; same claim storage versus new namespace with legacy detection; deterministic instance generation and Test Roll assumptions. Do not offer replacement/unique draws or nested tables without a separate approved requirement.

The requested separation, combined reward modes, final-activity-victory timing, and exactly-once delivery are requirements, not decisions awaiting renewed approval. The questions above resolve unspecified behavior within those requirements. Phase 2 implementation remains intentionally unstarted.
