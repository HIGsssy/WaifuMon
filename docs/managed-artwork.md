# Managed artwork

Artwork an admin uploads through the Portal, used by dungeon zones and enemies
without a commit or a deploy — plus the scene compositor that layers an enemy
sprite over a dungeon background for Discord.

`src/discord/dungeonArtwork.ts`, `portal/src/features/adminArtwork/`.

## Two kinds of artwork

| | Shipped | Managed |
| --- | --- | --- |
| Lives in | `assets/` in Git | `MANAGED_ASSETS_DIR`, outside Git |
| Reaches a server by | commit → deploy | upload in the Portal |
| Referenced by | a relative path (`artworkPath`) | an asset id (`artworkAssetId`) |
| Role | the default | an override |

Both are supported everywhere and nothing shipped is moved into the asset
table. Every reference resolves the same way
(`sceneLayers.ts`, `dungeonArtwork.ts`):

```
managed asset, while it is active
→ the shipped path under assets/
→ the next picture in the screen's precedence, and finally text
```

A managed asset that is unset, disabled, deleted or whose file is missing
falls through. Nothing in that chain is an error for a player.

## The asset model

`artwork_assets` — one row per logical asset. The bytes are **not** in
Postgres.

| Column | |
| --- | --- |
| `id` | UUID. The stable logical id that authored content references. |
| `category` | `dungeon_zone`, `dungeon_background`, `enemy_sprite`, `enemy_art`, `event_art`, `npc_portrait`, `equipment_art`. Drives pickers; nothing else. |
| `name` | Display label, editable. |
| `original_filename` | The uploader's base file name — a label only. |
| `mime_type`, `width`, `height`, `has_alpha`, `file_size` | Read from the bytes on upload. |
| `storage_key` | `<category>/<id>/<content_hash>.<ext>`, generated by the server. Never leaves the service. |
| `content_hash` | sha256 of the bytes: the ETag, the URL version, and the scene cache input. |
| `version` | 1 on upload, +1 per replacement. |
| `status` | `active`, `disabled`, or `deleted` (soft). |
| `uploaded_by`, `updated_by`, `created_at`, `updated_at`, `replaced_at`, `deleted_at` | Who and when. |

`artwork_asset_events` is the append-only audit trail: `upload`, `replace`,
`update`, `disable`, `enable`, `delete`, `reference_added`,
`reference_removed`, each with the admin's Discord id, the asset id, the old
and new hash where relevant, and a timestamp. A reference event names the
entity and field (`dungeon_zone:scrapheap_gauntlet`, `backgroundAssetId`).
Image bytes are never logged.

An enemy's managed artwork is two columns on its `combat_enemies` row — see
[Sprites, backgrounds and scenes](#sprites-backgrounds-and-scenes). The older
`combat_enemy_artwork` overlay table is kept as a record and no longer written
([enemies.md](enemies.md#the-old-overlay-table)).

## Storage, Docker and backups

Bytes go through `ArtworkStorage` (`artworkStorage.ts`): `put`, `get`,
`exists`, `delete` by storage key. V1 is `createLocalArtworkStorage`, a
directory. The database stores keys, never paths, so moving to S3 or
Cloudflare R2 is a second implementation of those four methods plus a one-off
copy of the directory to the bucket under the same keys — no schema change and
no change above the storage layer.

| Setting | Docker (compose) | Outside Docker (default) | |
| --- | --- | --- | --- |
| `MANAGED_ASSETS_DIR` | `/data/waifumon-assets` — named volume `waifumon-managed-assets` | `~/.waifumon/managed-assets` | **Stateful. Persistent. Back it up.** |
| `ART_CACHE_DIR` | `/data/waifumon-art-cache` — named volume `waifumon-art-cache` | `~/.waifumon/art-cache` | Disposable. |

Neither is under the Git working tree, and uploads must never be pointed at
one.

**Persistence.** Both are named volumes, so they survive `docker compose up
--build`, a deploy, a restart and `docker compose down`. The existing
`waifumon-card-cache-init` one-shot chowns them to `WAIFUMON_UID:WAIFUMON_GID`
before the bot starts, exactly as it does the card cache.
`docker compose down -v` (or `docker volume rm`) **destroys the uploads** while
the database still references them.

**Backups.** Managed uploads are application data, like the database, and the
two must be backed up and restored **together**: the rows describe the files.

```sh
# the database
docker compose exec postgres pg_dump -U "$POSTGRES_USER" "$POSTGRES_DB" > waifumon.sql
# the uploads
docker run --rm -v waifumon_waifumon-managed-assets:/data:ro -v "$PWD":/backup alpine \
  tar czf /backup/waifumon-managed-assets.tgz -C /data .
```

(The volume's full name carries the compose project prefix; `docker volume ls`
shows it.) `waifumon-art-cache` needs no backup.

A database restored without its artwork volume is safe but bare: every managed
reference falls back to shipped art, the server logs
`artwork-assets/missing-file` per asset it tries to read, and the Artwork
Assets page shows "the stored file is missing" — replacing the image repairs
the asset in place.

**Staging vs production.** Each environment has its own database and its own
volume. Asset ids are generated per upload, so they are *not* portable: a zone
exported from staging and committed to Git carries staging's asset ids, which
do not exist in production. Until promotion exists, either upload the same
images in production and select them there, or ship the art in Git and
reference it by path for content that travels between environments.

## Uploads: formats, limits, validation

| | |
| --- | --- |
| Formats | PNG, WebP, JPEG. Transparent PNG / WebP for sprites. |
| Not accepted | SVG, GIF, animated WebP, anything else. |
| Size | 8 MiB (`ARTWORK_UPLOAD_MAX_BYTES`). Larger is `413`. |
| Dimensions | 8 px to 4096 px per edge. |
| Recommended | Backgrounds 2400×1350 (16:9). Sprites: transparent, cropped close to the figure, about 1350 px tall. Zone / enemy full art: any aspect. |

`inspectImage` (`imageInspection.ts`) validates the **bytes**; the client's
file name and `Content-Type` are never trusted:

1. the leading bytes must be a PNG, JPEG or WebP signature;
2. `sharp` must decode it as that same format, as one still frame;
3. the declared dimensions are checked before any pixel is decoded, and
   `limitInputPixels` makes the decoder itself refuse a decompression bomb;
4. the image is decoded once, so a truncated or malformed body is refused.

A refusal is `400 ARTWORK_UPLOAD_INVALID` with a sentence the admin can act on.

## Replace, disable, delete

- **Replace** keeps the asset id. New bytes, new hash, `version + 1`,
  `replaced_at` set; the old file is removed. Every zone and enemy referencing
  the asset shows the replacement, and every URL and cache key derived from the
  hash changes. The event row records both hashes and both versions.
- **Disable** keeps the row and the file but takes the asset out of use: what
  references it falls back to shipped art. Always allowed; the response lists
  the references, the Portal says how many places now fall back, and each
  affected zone shows a warning. Re-enabling restores it.
- **Delete** is refused with `409 ARTWORK_ASSET_IN_USE` (and the list of
  references) while a zone or enemy still references the asset — clear them
  first, or disable instead. Otherwise it is a soft delete: the file is
  removed, the row and its history stay.

A zone cannot be saved pointing at an asset that does not exist
(`backgroundAssetId: that artwork no longer exists…`); pointing at a disabled
one is a warning.

## Serving and cache invalidation

`GET /admin/artwork/assets/:id/file` answers with the stored MIME type and an
`ETag` of the content hash. `If-None-Match` gets `304`. A URL carrying the
current hash (`?v=<hash>`) is `immutable`; any other is `no-cache`. Because the
hash changes on replace, neither a browser nor the Portal can keep showing a
replaced image.

Discord is sent attachments, not URLs. A managed image is attached as
`dungeon-art-<hash prefix>.<ext>` and a composed scene as
`dungeon-scene-<cache key prefix>.webp`, so a replacement is a different file
to Discord's CDN too.

## Sprites, backgrounds and scenes

**Enemy sprite.** A transparent cut-out of the enemy, separate from its full
artwork, meant to be layered over a background. Both images live on the enemy
in the Enemy Catalogue ([enemies.md](enemies.md)):

| | Managed (Portal) | Shipped (Git) |
| --- | --- | --- |
| Full artwork | `artwork_asset_id` | `artworkPath` |
| Sprite | `sprite_asset_id` | `spriteArtworkPath` |

Each managed image is optional and wins while set. The placement is a single
value on the enemy (`sprite_placement`), null for the default. No enemy needs a
sprite.

**Placement** (`scenePlacement.ts`) is a preset, not a canvas:

| Field | Range | Default |
| --- | --- | --- |
| `anchor` | `left`, `center`, `right`, `bottom-left`, `bottom-center`, `bottom-right` | `bottom-right` |
| `scaleBasisPoints` | 1000–10000: the sprite's height as a share of the scene's | 8500 |
| `offsetX` | −600…600 px | 0 |
| `offsetY` | −337…337 px | 0 |

Width follows from the sprite's own aspect ratio — it is never stretched — and
the result is clamped inside the canvas.

**The player's Buddy.** A fight scene has one more actor, and it is not
authored anywhere — not on a zone, a room or an enemy, and not in the enemy
catalogue. It is resolved at render time:

| | |
| --- | --- |
| Who | the run's fighter snapshot — `dungeon_runs.fighter.speciesSlug`, frozen at run start. Changing the active Buddy mid-run changes nothing. |
| Image | the species' dungeon sprite, by convention: `assets/waifumon/<slug>/<slug>_sprite.webp` (`speciesDungeonSpritePath`). It is the `AssetId` variant `<slug>_sprite` in the existing species artwork layout — no second registry, no stored path. |
| Where | the reserved player side: `PLAYER_BUDDY_PLACEMENT` — `bottom-left`, 80% of the scene's height, no offsets — through the same `layoutSprite` arithmetic as an enemy (`layoutPlayerBuddy`). |
| Bound | never wider than 40% of the canvas (`PLAYER_BUDDY_MAX_WIDTH_SHARE`); a wide sprite shrinks in proportion and stays on the floor line. |

Both constants live in `scenePlacement.ts`; moving her is changing them and
nothing else. A species with no sprite file is left out of the scene — the
frame still renders, `dungeons/buddy-sprite-missing` is logged once per species
with the slug and the expected path, and her card art is **never** substituted.
A sprite file that will not decode is handled the same way
(`scene/player-buddy-omitted`).

Enemy placement is unchanged: all six anchors remain. An enemy at its default
(`bottom-right`) never touches her. One authored into the left side is allowed
and drawn over her; the scene preview draws a stand-in Buddy and warns when the
enemy's box covers 15% or more of hers (`PLAYER_BUDDY_COLLISION_SHARE`).

**Background pool.** A zone's `backgrounds` is a list of
`{ id, assetId | artworkPath, weight, enabled, minDepth, maxDepth }` — each
names exactly one image, managed or shipped. When a run is **generated**, every
node draws one background by weight from the enabled entries covering its depth
(`dungeonScenes.ts`). The draw uses its own random stream derived from the run
seed, so the same seed reproduces the same backgrounds and the graph's own
stream — and therefore every existing seed's graph — is untouched. A node no
background covers uses the zone background.

**Composition** (`sceneComposition.ts`) is independent of dungeons: it takes a
background layer, an optional sprite layer with a placement, an optional
player-Buddy layer, and an output size, and returns a cached raster.

- **Layer order**, bottom to top (`SCENE_LAYER_ORDER`): background → player
  Buddy → enemy sprite. There are no scene overlays; combat text and controls
  are the Discord embed's, outside the image.

- **Direct raster composition with `sharp`** — not SVG. No SVG document is
  built and no uploaded markup is ever interpreted; layout is integers from
  `layoutSprite`.
- **Output**: 1200×675 (16:9) WebP — the one canonical scene size. The
  background is scaled to cover and cropped, the sprite scaled by height.
- **Cache**: `sha256(renderer version, background hash, sprite hash,
  placement, output size)` — plus the Buddy sprite's hash and her reserved
  layout when she is in the scene — names a file under `ART_CACHE_DIR`. The same inputs
  reuse it; a replaced asset has a new hash and so a new key. Nothing is
  rendered up front. The directory can be emptied at any time — a missing file
  is rendered again. Concurrent requests for one scene share one render.
- **Cost**, measured on a 2400×1350 background and a 900×1200 sprite: upload
  validation ≈ 190 ms, first composition ≈ 215 ms, cached ≈ 1 ms. Rendering is
  synchronous inside the interaction that needs it and well inside Discord's
  3-second window; there is no background queue.

`sharp` was already a dependency (card rendering); it ships prebuilt musl
binaries, so the `node:22-alpine` image needs no build tools and no new
packages. No browser renderer is involved.

**What a Delve screen shows**, first match wins (`dungeonArtwork.ts`):

| Screen | 1 | 2 | 3 | 4 | 5 | 6 |
| --- | --- | --- | --- | --- | --- | --- |
| Fight | background + the run's Buddy + enemy sprite, composed | enemy full artwork | the node's background alone | zone artwork | zone background | text |
| Event, rest, reward, exit | the event's own artwork | the node's background alone | zone artwork | zone background | text | |

For the composed scene the background is the node's snapshotted one, else the
zone background. Neither an enemy nor the Buddy is composed onto a non-combat
node, and a fight that falls back past the composed scene (an enemy with no
sprite) shows no Buddy sprite either. Her card art remains the thumbnail.

**Snapshots.** When a run starts it records, in `dungeon_runs.zone_snapshot`:
`scenes` (each node's chosen background — pool entry id, asset id or path) and
`enemyArtwork` (each placed enemy's full-art asset, sprite asset and
placement). These are *logical* references:

- the choice — which background, which sprite, where it stands — never
  changes for that run, whatever an admin edits afterwards, and is never
  re-rolled by a repaint;
- the *image behind* an asset id is read live, so replacing it updates an
  active run too (immutable per-version snapshots would mean keeping every old
  file; the hash-keyed cache makes the live read cheap and correct);
- an asset disabled or lost mid-run falls back down the list above.

## Security

- Every route needs `artwork.read` or `artwork.write`, checked per request
  (setting an enemy's artwork is an enemy save: `enemies.write`). Ordinary players
  hold neither; the shared API token is refused unless
  `PLATFORM_API_ADMIN_BEARER` is on.
- Writes from a cookie session carry the CSRF token like every other admin
  write.
- The upload body limit is enforced by the route (and by Nginx, a little above
  it, so the API's JSON 413 is what a caller sees).
- Stored names are server-generated from the category, a UUID and a hash; the
  local store validates each key's shape and confines the resolved path to its
  root. A client file name is reduced to a base name and kept as a label.
- Nothing uploaded is executable or served as a document: only three raster
  types are accepted, and bytes are served with their stored `Content-Type`,
  `X-Content-Type-Options: nosniff`, `Content-Security-Policy: default-src
  'none'; sandbox` and `Cross-Origin-Resource-Policy: same-origin`.
- The scene preview accepts only an asset id or a path under `assets/` — never
  a URL — and composes only local files.

## Admin Portal

| Page | Permission | |
| --- | --- | --- |
| `/admin/artwork` — Artwork Assets | `artwork.read` | **Upload** (category, optional name, file), **Browse** (category filter, search, thumbnails, dimensions / type / size), **Manage** the selected asset: rename, move category, replace, disable / enable, delete, copy id, where it is used, history. |
| `/admin/dungeons/zones/:key` | `dungeons.read` | **Zone Artwork** (uploaded override + shipped path for both images), **Background Pool**, **Scene Rules** with a composed preview. |
| `/admin/enemies/:key` — Enemy editor | `enemies.read` | Per enemy: **Full artwork**, **Transparent sprite** and **Default placement**, uploaded or selected in place. `/admin/dungeons/enemies` redirects to `/admin/enemies`. |

An artwork field offers **Select…** (a picker opened on that field's
category), **Upload…** (validate → store → create → selected, without leaving
the editor) and **Clear** (back to the shipped path, which the field names).
Asset ids are never typed. The previews are rendered by the server with the
production compositor.

## API

Under `/api/v1/admin`.

| Method | Path | Permission | |
| --- | --- | --- | --- |
| GET | `/artwork/meta` | `artwork.read` | limits, categories, scene size, placement bounds |
| GET | `/artwork/assets?category=&status=&q=&limit=&offset=` | `artwork.read` | list |
| GET | `/artwork/assets/:id` | `artwork.read` | asset, references, history |
| GET | `/artwork/assets/:id/file?v=` | `artwork.read` | the bytes |
| POST | `/artwork/assets?category=&filename=&name=` | `artwork.write` | upload — the body is the image |
| PUT | `/artwork/assets/:id/file?filename=` | `artwork.write` | replace — the body is the image |
| PATCH | `/artwork/assets/:id` | `artwork.write` | `{ name?, category? }` |
| PUT | `/artwork/assets/:id/enabled` | `artwork.write` | `{ enabled }` → asset and its references |
| DELETE | `/artwork/assets/:id` | `artwork.write` | 409 while referenced |
| POST | `/artwork/scene-preview` | `artwork.read` | `{ background, sprite?, placement?, playerBuddy?: { speciesSlug? } }` → WebP. With `playerBuddy`, a Buddy is drawn in the reserved side (the named species, else the first with a sprite) and `x-scene-player-buddy`, `-overlap` (0–100) and `-collision` headers report her and the enemy's overlap |
| PUT | `/enemies/:key` | `enemies.write` | an enemy save carries `artworkAssetId`, `spriteAssetId`, `spritePlacement` ([enemies.md](enemies.md#admin-api)) |

## Not built yet

- Object storage (S3 / R2) and a CDN — the storage interface is ready for it.
- Promoting managed assets between environments (export / import with bytes).
- Managed artwork for events, NPCs and Equipment: the categories exist and
  uploads work, but nothing references them yet.
- Per-zone or per-pool-entry sprite placement overrides.
- A drag-and-drop scene editor, animation, layered or skeletal sprites.
- Pruning the scene cache by age or size (it can be emptied by hand).
- Keeping replaced versions of an image.
